# KN-95, the output head on WebGPU in integers

| Claim | Evidence | Level |
| --- | --- | --- |
| The guest prints the dense kernel's text as `renderKernel` does | `dense_accumulate_code_prints_tree` in `app/src/Proofs/GpuCode.lex.tex` | proved by Lean in the gate |
| The quantiser, the dense kernel and the rounding kernel give `hologram_ai_exact`'s rows | `dense_row_matches_exact` in `app/src/Proofs/GpuQ4Chain.lex.tex` | checked on a fixture |
| Decision 48 prints it as kernel 6, and only with no units or width | `kernel_kn_95`, the app recipe's replay of `claims/048.json` | tested |

Why: the head is a quarter of a token's work, and it is dense, its weights
halves, so the q4 product's kernels cannot run it. With it on the module,
every token went back to the CPU once.

How: `denseAccumulate` in `app/src/Engine/Gpu.lex.tex` is the q4 accumulator
with three changes. It reads each input's own 16-bit code where the
accumulator reads a group sum, its own half weight where the accumulator reads
a group's scale, and the power of the input's group; and it walks a row of up
to 2048 inputs as 64 groups of 32, skipping every group past the row's width.
The sum it builds is the one `dense_product_with` builds, each product placed
at its exact bit position in the same 384-bit register, so the rounding
kernel rounds it once as before.

The fixture is the q4 product's 32 activations and two rows of 32 half weights
drawn by a fixed generator, with a zero, two subnormals and the largest finite
half among them; `dense_product_with` gives the expected rows.

Why 64 groups of 32 and not one loop: Lean evaluates the kernel lazily, so
each step of a loop it runs nests one level deeper, and a single loop of 2048
steps passed Lean's recursion limit. Skipping the groups past the width keeps
the steps a fixture runs near the q4 accumulator's, and on a GPU skips work
that would do nothing.

Not proved: that the kernel equals its stage for every input in bounds, as for
KN-73.
